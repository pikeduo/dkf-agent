# DKF-Agent Knowledge Service 后续开发计划（简明路线图）

> **给 Codex 的说明**：这是一份开发方向与阶段目标说明，不是逐条照做的任务清单。请结合仓库实际代码和开发进度，自主决定技术方案、模块拆分、实现顺序、测试方式与必要的优化。优先复用现有功能，不必严格按照本文的表述实现。
>
> **项目位置**：`D:\python project\dkf-agent`  
> **当前起点**：用户已确认，阶段 33 的 **200 份文档全部入库**。后续开发重点转向检索效果、真实问答质量、赛题专项能力、性能以及独立演示，不再把批量导入和 Adapter 排错作为主要任务。  
> **适用范围**：仅限本人负责的 **非结构化知识问答 Knowledge Service**。

## 一、开发范围

本模块面向赛题八中的非结构化、多格式文档问答，主要负责：

- 多格式文档知识库，以及必要的解析质量与结构保留能力。
- Dense、BM25、Hybrid、Reranker 检索及效果优化。
- 单文档、多文档 RAG 问答，答案生成、证据引用、可解释性及多轮使用体验。
- 公式识别、参数绑定与安全计算。
- 不规范目录识别、文档复杂度评估、文档质量评估等非结构化赛题任务。
- Knowledge Agent 内部工具编排、性能评测、Demo、独立部署与技术资料。

**不负责** NL2SQL、Schema Linking、Coordinator Agent、跨结构化与非结构化数据的 Fusion Agent，以及其他成员的业务模块。可以保留清晰的 API/Agent 接口，方便后续团队联调，但不必替其他模块开发功能。

目前仓库已有 MinerU/Native Parser、Block/Chunk、BGE-M3、pgvector、BM25、RRF、BGE Reranker、LlamaIndex RAG、Evidence/Citation、公式计算以及 LangGraph Knowledge Agent 等基础。Codex 应先阅读源码，判断实际完成度，避免重复实现。

## 二、总体阶段安排

| 阶段 | 主要方向 | 期望成果 |
|---|---|---|
| **33（收尾）** | 全量检索效果评测与优化 | 200 文档、4,087 QA 的四策略对比及结果分析 |
| **34** | RAG 答案质量与可解释性 | 单/多文档问答、忠实度、答案正确性和引用评测 |
| **35** | 非结构化赛题专项能力 | 公式、目录层级、文档复杂度、文档质量与鲁棒性成果 |
| **36** | 性能与稳定性 | 不同知识库规模、并发、响应时间及瓶颈分析 |
| **37** | Knowledge Service 独立 Demo | 可交互展示检索、问答、证据、公式和上传 |

阶段编号沿用现有 `docs/DEVELOPMENT_PLAN_CODEX.md`。可以按依赖关系合理调整先后、合并相关工作，优先处理对实际问答体验影响最大的短板。

## 三、阶段 33：完成全量检索评测

**目标**：确定现有检索系统在真实公开数据集上的效果，找出最值得优化的环节。

工作方向：

- 利用已经入库的 **OHR-Bench 100 份 PDF / 3,588 QA** 和 **Microsoft OCB 100 份 Office / 499 QA**，评估现有检索链路。
- 对比 **Dense（BGE-M3）、BM25、Hybrid（RRF）、Hybrid + BGE Reranker** 四种策略。
- 统计 Recall@5、Recall@10、MRR@20 等检索指标，并按数据集和文档类型分析表现。
- 关注表格、长文档、跨页、公式、语义表达差异等实际失败案例，有价值时优化检索、切片或重排策略。
- 根据当前数据库状态选择合理的评测方法；如果存在 `PARTIAL_READY`，应如实标记质量限制，避免把部分可用文档说成完整解析。

**阶段成果**：一份可复现的检索评测报告、四策略对比结果、典型失败案例与必要的代码改进。

已有工具可从 `scripts/evaluate_stage33.py`、`scripts/stage33_*.py` 和 `docs/STAGE33_EVALUATION.md` 开始了解。具体实现与评测组织方式由 Codex 自行安排。

## 四、阶段 34：RAG 问答与答案质量

**目标**：不仅能找到文档，还要真正答对问题，并说明答案来自哪里。

工作方向：

- 验证和完善单文档、指定多文档以及全知识库问答。
- 评测 **Answer Accuracy、Faithfulness、Citation Accuracy**；重点关注数字、单位、表格数据、公式及原文依据。
- 验证文件名、页码/章节、引用片段、来源追溯和证据不足时的合理拒答。
- 增强多文档证据组织、问题歧义处理，以及 Knowledge Agent 内部的多轮交互体验。
- 设计适当的真实问答样本、错误案例和评估流程，结合自动化与人工检查。初赛至少准备 10 个正式单文档问答案例；忠实度以赛题的 **90%** 作为努力目标。

**阶段成果**：能演示且有真实测试结果的 RAG 问答能力、引用验证能力和质量分析报告。

注意区分检索指标、生成答案正确性及引用来源正确性。OCB 的 `expected_assertions` 不应直接当作现成标准答案，评测方式可结合其原始定义设计。

## 五、阶段 35：非结构化赛题专项功能

结合赛题中级任务 6～9，优先做出有实际效果、可以测试和展示的功能。无需机械地为每项单独重建大系统，已有基础能复用就复用。

### 任务 6：公式识别、参数绑定与计算

完善从文档检索公式、识别变量、结合用户提供或有来源的参数进行计算的流程。重点考察公式是否正确、参数来源是否明确、计算结果是否可靠，以及计算过程能否解释。优先基于现有公式服务和 SymPy 实现。

### 任务 7：不规范目录与标题层级识别

探索对标题混乱、目录不完整、层级不规范文档的结构恢复。可结合解析时的布局、字体、章节文本或其他合理特征，改善文档结构理解和检索效果。

### 任务 8：文档复杂度评估

基于文档类型、页数、表格/公式数量、布局复杂程度等信息设计可解释的复杂度评估能力，用于分析解析难度或辅助选择处理策略。

### 任务 9：文档质量评估

针对扫描件模糊、倾斜、阅读顺序异常、图表或 OCR 内容缺失等问题，形成质量提示或分级评价，并使用典型样本验证有效性。

**阶段成果**：形成若干可演示的专项能力，以及每项的基本评价方法、实际案例和效果说明。具体优先级由 Codex 结合现有代码、赛题价值和时间自主决定。

## 六、阶段 36：性能、并发与鲁棒性

**目标**：了解系统在真实使用中的速度、资源消耗和稳定性，优化最明显的瓶颈。

工作方向：

- 记录 Query Embedding、Dense/BM25、融合、重排、LLM 生成等主要步骤耗时。
- 对不同规模的知识库进行实验，尽可能覆盖赛题决赛要求的 **至少三种规模**。
- 适当评估并发查询、长文档、高密度表格、低质量文档和异常恢复。
- 分析 CPU/GPU/内存、数据库、模型调用和解析成本，优先解决对体验影响较大的问题。

**阶段成果**：性能与鲁棒性报告、关键瓶颈分析和优化前后的数据对比。

## 七、阶段 37：独立 Knowledge Service Demo

**目标**：形成一个不依赖其他成员模块、可以现场展示的非结构化知识问答系统。

建议展示以下能力：

- 选择知识库、文档，输入自然语言问题并获取答案。
- 单文档、多文档与跨文件格式问答。
- 查看检索结果、引用文档、页码/章节、证据片段及必要的工具执行过程。
- 展示公式识别、参数输入和计算结果。
- 演示新文档上传、解析、索引后参与问答。
- 选择合适的文档质量、复杂度或目录恢复案例，展示中级任务成果。

Demo 的技术形式与界面设计由 Codex 根据项目现有结构决定，以**稳定、清楚、便于评委理解**为优先，不需要为了演示重写后端。

**阶段成果**：可启动的独立 Demo、若干真实演示案例和简明操作说明。

## 八、阶段 38：独立验收与交付

**目标**：让 Knowledge Service 能够独立部署、复现测试、演示和交给队伍联调。

工作方向：

- 整理当前服务的启动、配置、依赖和运行说明。
- 验证现有知识库问答、动态上传、检索、证据、公式、Knowledge Agent 等主要能力。
- 汇总各阶段真实实验结果，准备系统架构、关键技术、数据集、效果分析与典型演示案例。
- 形成稳定的 Knowledge Search / Query / Formula / Agent 接口说明，供其他成员使用。
- 为比赛报告、PPT 和演示录屏整理可直接引用的材料。

**阶段成果**：可以独立运行的 Knowledge Service、清晰的接口与部署文档、测试报告及比赛展示素材。

## 九、Codex 的工作方式

1. **发挥自主性**：先了解仓库现状，自己决定实现细节、代码组织、验证方法和阶段内的子任务。发现更合理的方案可以调整计划，并说明原因。
2. **复用优先**：重点提升现有系统效果，而不是重写已实现的 Parser、RAG、公式或 Agent 链路。遇到真实缺陷可以修复，但不要无原因地返回大规模入库排错。
3. **以真实效果为导向**：尽量有可复现的测试、实验结果和失败案例；不必为了形式完成大量低价值文档。
4. **适度汇报**：可以持续推进同一阶段的相关开发，不需要每个小修改都停下来请示；阶段或重要里程碑完成后说明做了什么、结果如何、还需要什么。
5. **保留必要的安全边界**：尊重 `AGENTS.md` 与现有项目约定；涉及付费云调用、未授权数据外传、破坏性数据库操作、批量重解析/重建索引等，先向用户确认。不要编造测试成绩或把部分质量结果标记为完整成功。
6. **技术选择灵活**：可以基于已有 LlamaIndex、LangGraph、BGE-M3、pgvector、SymPy 等组件优化，也可以提出其他合理实现；不因本计划某处举例而限制必要的工程判断。
